# 数据结构与兼容协议

范围：固定提交原生 1.6.0 build10 的 `OrbitCore`。本文件的示例为合成数据，不能用于替换用户正式数据库。

## 1. 统一编码规则

- 文本使用 UTF-8 JSON；Swift Data 通过 JSON Codable 表示为标准 Base64 字符串。
- 业务日期为严格公历 `YYYY-MM-DD`，按 `Asia/Shanghai` 解析。拒绝 2026-02-29、2026-04-31、2026-1-01 等非法日期。
- 任务时间戳和 exportedAt 为 ISO 8601，生成时带毫秒 UTC；解析兼容有/无小数秒的互联网日期时间，不能比较未经解析且时区不同的字符串来决定先后。
- 字段长度中 UTF-16 单位与 UTF-8 字节的规则必须区分；一个 emoji 往往占 2 个 UTF-16 单位。名称里的“字”是 UI 提示，不代表按 Unicode grapheme 数计限。
- `due=""` 代表未设置，`startDate=nil` 代表未设置，不能替换为 1970 年或今天。
- 已完成 iff `status==done` 且 `completedAt!=nil`，两者必须一致。自定义状态不代表完成。

## 2. 任务字段

| 字段 | 类型/编码 | 必有/默认 | 校验和语义 |
|---|---|---|---|
| id | String | 必有；默认 UUID 字符串 | 非空，UTF-16 <200；整库唯一；导入保持原 ID |
| title | String | 必有 | 原输入 UTF-16 <=100；保存去首尾空白后非空 |
| description | String | 必有；空字符串 | 普通说明镜像，UTF-16 <=5000，参与搜索/摘要 |
| richDescription | Data → Base64 | 可省略/nil | flat RTFD，最多 24 MiB；不能当 HTML 或裸 RTF 解释 |
| category | String | 必有；work | work / personal / life |
| status | String | 必有；todo | todo / doing / done / custom:名称；必须在定义列表中 |
| priority | String | 必有；medium | high / medium / low |
| due | String | 必有；"" | 空或有效日期；真实截止日期 |
| startDate | String? | 可省略/nil | 有值必须日期有效；有 due 时 <=due |
| createdAt | String | 必有 | 有效时间戳，已有任务编辑不得重置 |
| updatedAt | String | 必有 | 有效时间戳，成功业务更新时改变 |
| completedAt | String/null | 导出未完成必须显式 null | 已完成才有有效值；重开清空 |
| projectID | String? | 可省略/nil | 非空引用必须存在于 projects |
| attachments | Array | 旧数据缺省为 [] | 无附件导出可省略；有附件完整保留 |

校验不强制 ID 一定符合 UUID 格式，HTML 导入文件可使用自定义字符串 ID。不能在导入时全部重建 ID，否则合并、历史引用与内容指纹会改变。当前校验不强制 updatedAt>=createdAt，也不依赖时间戳排序证明用户时钟正确；须接受符合这些字段约束的合法备份。

## 3. 附件与项目

| 附件字段 | 规则 |
|---|---|
| id | 非空，UTF-8 <=200 字节；同任务内唯一 |
| name | 非空，UTF-16 <=255；不可含 `/`、反斜杠、控制字符，不可为 `.`/`..` |
| typeIdentifier | 非空，UTF-8 <=200 字节；原生 UTI，如 public.png / public.data |
| data | Base64 原始字节；单个 <=10×1024²，任务合计 <=20×1024² |
| 数量 | 每任务 <=20；不能把同名文件一律去重，唯一性按 id |

| 项目字段 | 规则 |
|---|---|
| id | 非空，UTF-16 <200；最多 10,000 个，ID 唯一 |
| name | 去首尾空白、NFC、1～60 UTF-16、无控制字符；名称不重复 |
| 顺序 | projects 数组/SQLite rowid 读取顺序，是甘特图分组顺序 |

UI 保存时同名项目使用本地化大小写不敏感比较，备份校验主要使用规范化名称小写去重；不同语言的大小写/重音比较在新平台可能略有差异，要使用相同样本核验，不假设普通 ordinal 等同于 localizedStandardContains。

## 4. 状态定义

内置顺序初始为 `["todo","doing","done"]`；允许用户列排序后顺序变化。内置必须全部存在，状态列表总数 <=100、raw 值唯一、规范化小写显示名唯一。

自定义 raw 值为 `custom:` + 已校验名称。名称不能有首尾空白、控制字符，UTF-16 1～20，不能与“待办/进行中/已完成”冲突。业务新增路径先 trim + NFC，插在当前 done 前。

disabledStatuses 是状态 raw 值数组，不能重复，只能引用存在的自定义状态。内置不能出现在停用数组。显示状态 = 启用状态 + 被全库任务引用的停用状态；顺序始终遵守完整定义列表。

## 5. TaskBackup JSON 信封

| 字段 | 类型 | 含义/缺省 |
|---|---|---|
| app | String | V1使用ORBIT，V2～V6使用Space；decode不将app值作为严格拒绝条件 |
| version | Int | 支持 1～6；未来版本拒绝 |
| exportedAt | ISO 8601 String | 导出时间；GitHub portable 固定为 Unix epoch 的字符串 |
| tasks | Array | <=10,000，唯一 ID，每条完整校验 |
| statuses | Array<String>? | 缺省为内置列表 |
| projects | Array<Project>? | 缺省 [] |
| disabledStatuses | Array<String>? | 缺省 [] |
| settings | Object<String,String>? | 缺省 {}；<=256 项 |
| workspaceID | String? | 工作空间标识 |
| revision | String? | 乐观并发修订，不作为跨设备内容等价依据 |

settings key UTF-8 <=100 字节，value UTF-8 <=8192 字节。未知 JSON 字段可能被 Codable 忽略，因此载荷字段必须与文件格式版本对应；不支持字段的读取端必须拒绝写回，避免数据丢失。

### 5.1 导出版本选择顺序

| 版本 | 触发内容 | app |
|---|---|---|
| V1 | 只有内置默认状态及普通旧任务，没有扩展上下文 | ORBIT |
| V2 | 状态定义不等于内置默认顺序（含自定义/重排） | Space |
| V3 | 项目、停用状态、非空 settings 或 workspaceID | Space |
| V4 | 任意任务有附件 | Space |
| V5 | 任意任务有 startDate | Space |
| V6 | 任意任务有 richDescription（即使 data 为空但非 nil） | Space |

按表顺序向上取需要的版本；实际数据库状态有 workspaceID/settings，所以日常普通导出通常至少 V3，不应把“没有图片就必须 V1”写死。是否有富文本取决于编辑器是否生成该字段，纯文字经富文本编辑器保存也可能是 V6。

导入拒绝版本标识与内容矛盾：V1 自定义/状态定义、V1～2 项目或设置、V1～3 附件、V1～4 开始日期、V1～5 富文本。拒绝未定义状态/项目引用、重复任务 ID、无效完成组合、过大文件。整份验证后才能弹确认或写库。

### 5.2 V1 格式示例

```json
{
  "app": "ORBIT",
  "version": 1,
  "exportedAt": "2026-11-02T00:00:00.000Z",
  "tasks": [{
    "id": "example-task-1",
    "title": "示例：整理资料",
    "description": "用于兼容测试，不含个人数据",
    "category": "work",
    "status": "todo",
    "priority": "medium",
    "due": "",
    "createdAt": "2026-11-01T02:00:00.000Z",
    "updatedAt": "2026-11-01T02:00:00.000Z",
    "completedAt": null
  }]
}
```

V6 真实 RTFD 必须由可用编辑器生成并做 round trip；不能把普通字符串 Base64 后填 richDescription 来伪造合法富文本。本资料包提供的字段说明不表示任意 Base64 都能被 AppKit 正确打开。

## 6. SQLite 表与元数据

文件名 `space.sqlite`；上一份 `space.previous.sqlite`；文件头 `SQLite format 3` + NUL。新建设置 `application_id=1397768515`，user_version 初始 1。当前 readState 主要校验 user_version、quick_check 和字段/引用，没有单独强制 application_id；新平台写兼容库时仍须正确设置标识。

```sql
CREATE TABLE metadata(key TEXT PRIMARY KEY,value TEXT NOT NULL);
CREATE TABLE statuses(
  id TEXT PRIMARY KEY,
  position INTEGER NOT NULL,
  active INTEGER NOT NULL CHECK(active IN (0,1))
);
CREATE TABLE projects(id TEXT PRIMARY KEY,name TEXT NOT NULL UNIQUE COLLATE NOCASE);
CREATE TABLE tasks(
  id TEXT PRIMARY KEY,
  status_id TEXT NOT NULL REFERENCES statuses(id),
  project_id TEXT REFERENCES projects(id),
  payload TEXT NOT NULL
);
CREATE INDEX task_status ON tasks(status_id);
CREATE INDEX task_project ON tasks(project_id);
CREATE TABLE settings(key TEXT PRIMARY KEY,value TEXT NOT NULL);
```

- metadata 至少包含 `workspaceID`、`revision`，revision 每次成功事务使用新的 UUID 文本。
- tasks.payload 是单个完整 OrbitTask 的 JSON 文本，含 Base64 附件/富文本；没有外部附件文件夹依赖。
- 读取 statuses 按 position；projects、tasks 按 rowid；所有 payload 再走逻辑校验。写入逻辑必须让冗余的 status_id/project_id 与 payload 对应一致。
- 启用 `foreign_keys=ON`、`trusted_schema=OFF`，busy_timeout=5000 ms，打开 FULLMUTEX。
- 读取 `PRAGMA quick_check` 必须为 ok。新平台可加强完整性验证，但不能对损坏库无提示初始化空库。

### 6.1 SQLite 文件格式要求

| user_version | 内容能力 |
|---|---|
| 1 | 既有字段、项目/状态、附件 |
| 2 | 保存过显式开始日期 |
| 3 | 保存过富文本 |

当前写入版本 = max(已有版本,本次任务所需版本)；撤销开始日期/富文本后不降文件版本。读取支持1/2/3；不支持所需格式的客户端拒绝读取，保护字段。SQLite user_version 和 JSON version 不是同一套编号。

## 7. 保存、快照和并发

1. 内存构造完整候选状态；校验总量、字段、状态/项目引用及设置。
2. 用户级目录确保存在；原版目录权限 0700，数据库/快照 0600。
3. 使用 `.sqlite-write-lock` + flock 独占协调同应用多进程；目标平台提供等价进程锁，不能只在 UI 线程加 mutex。
4. 核对库中 revision 等于 expectedRevision。
5. 使用 SQLite Backup API 导出上一份，包含已提交 WAL；不可只复制主文件忽略 WAL。
6. BEGIN IMMEDIATE，事务内再次核对 revision；删除/按引用顺序重写业务表；设置新 revision；COMMIT。
7. 成功后更新内存 state 与 expectedRevision。异常 ROLLBACK，保持旧内存数据。

偏好保存：同样加锁、BEGIN IMMEDIATE、revision 校验，但只重写 settings 与 revision，不改任务表，不覆盖 previous。导出快照需拒绝目标等于活动库或 previous，检查 revision 并原子写目标。

读取失败后设置未载入状态；普通保存禁用。用户明确导入有效备份恢复时 allowRecovery 才允许创建替代库，并保留损坏原文件到 previous；不把坏文件直接删除。导入恢复的文件自身应先验证。

## 8. JSON导入与偏好设置

没有 space.sqlite 而存在 tasks.json 时读取校验、保留原件，并仅在不存在时生成 tasks.before-sqlite.json；临时创建数据库、事务写入、重读成功后原子 rename。已有数据库时不重新从旧 JSON 覆盖。

旧 UserDefaults 迁移 dark、navCollapsed、overviewCollapsed、listMode，并设 preferencesMigrated；新版优先 viewMode，再兼容 listMode。下列设置以字符串保存：

| 设置 | 值及缺省 |
|---|---|
| dark | true/false；首次 false |
| navCollapsed | true/false；首次 true |
| overviewCollapsed | true/false；首次 false |
| viewMode | board/list/gantt/calendar；首次 board |
| calendarMode | day/week/month；首次 month |
| preferencesMigrated | true，避免重复迁移 |
| sync.location / sync.username | 手动快照目标及用户名；不含密码 |
| sync.lastReceipt / sync.appliedReceipts | 最近及最多 64 条 receipt，竖线分隔 |

临时查询、甘特 anchor、日历 selected/anchor、甘特项目收展、拖动指针、未保存草稿、撤销层和通知不持久化。GitHub 连接/基线在独立 github-sync.json，凭据在系统安全存储；这些都不在 SQLite settings 中。

## 9. 排期与查询算法核对

今日由北京时间日期计算，每 30 秒检查但只有跨日才发布更新；重新激活也检查。未完成且 due 空的默认结束 = (startDate 或 today)+5 个公历日；已完成且 due 空的结束 = 完成日；其他用真实 due。显示开始 = min(显式 startDate 或默认推导开始,显示结束)。天数为日期差 +1。

排序不可依赖数据库偶然 rowid 作为平局规则。查询排序详见主 PRD；ID 最终升序用于稳定结果。区间判断均闭区间；周历周一开头，日期选择器周日开头。

## 10. 富文本移植的强制保护

目标平台如使用另一种编辑器，至少做到：普通文本搜索镜像正确；粗体/下划线/内嵌图顺序可还原；保存/导出/同步时不丢原始 RTFD 字节。要宣称与 macOS 双向编辑兼容，必须将真实图文样本跨平台导出后由 AppKit 重读，并反向测试。

只保留 RTFD 原字节但无法显示/编辑，属于“无损携带，编辑能力缺失”；把 RTFD 转成 HTML/Markdown 后无法回写，属于“单向转换”。两者都不能标为完整富文本复刻。可选路线是实现兼容 codec 或明示只读保护，再另行定义新协议；不得用同一个 V6 版本号偷偷改变字段编码。
